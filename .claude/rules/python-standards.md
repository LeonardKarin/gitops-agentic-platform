# Python standards

Apply these rules to all Python files in this repository.

## Core Python rules

- Follow PEP 8.
- Use 4 spaces per indentation level.
- Never use tabs in Python files.
- Maximum line length is 99 characters for code.
- Maximum line length is 79 characters for comments and docstrings.
- Use implicit continuation inside parentheses, brackets, or braces.
- Do not use backslash line continuation except when strictly unavoidable.
- Use 2 blank lines between top-level definitions.
- Use 1 blank line between methods inside a class.
- Keep functions focused and reasonably short.

## Imports

- Group imports in this order:
  1. standard library
  2. third-party packages
  3. local project imports
- Separate each import group with one blank line.
- Prefer one import per line.
- Never use wildcard imports such as `from module import *`.

## Type annotations

- All public functions and methods must use type annotations.
- The repository baseline is Python 3.8+ compatible.
- Use `Optional[T]` instead of `T | None`.
- Prefer explicit collection types such as `Dict[str, Any]`, `List[str]`, and `Tuple[...]`.
- Use `Callable[..., Any]` instead of bare `callable` in type hints.

## Naming

- Modules: `snake_case`
- Functions and methods: `snake_case`
- Private helpers: `_snake_case`
- Classes: `PascalCase`
- Constants: `SCREAMING_SNAKE_CASE`
- Type aliases: `PascalCase`

## Documentation

- Public modules, classes, and functions must use Python docstrings.
- This repository uses Doxygen-style tags inside docstrings when documenting public code.
- Module docstrings should describe purpose, main dependencies, and thread-safety or idempotency constraints when relevant.
- Public class docstrings should document behavioral guarantees and safety constraints.
- Public function docstrings should document parameters, return values, raised exceptions, and sensitive-data handling where relevant.

## Error handling

- Use specific exception types.
- Never use bare `except:`.
- Avoid `except Exception:` unless you re-raise or log with clear context.
- Preserve the original exception when re-raising.
- Log operational context, not secrets.

## Security and confidentiality

- Never log passwords, API tokens, secrets, raw vault material, or confidential payloads.
- Never persist decrypted credentials longer than necessary.
- Do not store decrypted credentials in long-lived instance attributes.
- Redact or avoid logging sensitive request and response bodies.

## Filesystem and output

- Prefer `pathlib.Path` for all new filesystem code.
- Avoid manual path concatenation.
- Output generated by aggregators or exporters should be treated as INTERNAL by default unless explicitly reviewed otherwise.

## Project-specific aggregator and FSM rules

Apply the following rules in aggregator-related Python modules such as `aggregator/`, `aggv2/`, and similar worker orchestration code:

- Document thread-safety guarantees in module or class docstrings.
- Guard shared mutable state with a lock.
- Use explicit worker signaling primitives such as `threading.Event` where applicable.
- Never mutate shared collections across threads without synchronization.
- State names must use `SCREAMING_SNAKE_CASE`.
- Do not transition to terminal states without updating the associated worker completion flag or equivalent completion marker.

## Project-specific credential handling

- When using vault or obfuscation helpers such as `secrets-vault`, treat returned secrets as confidential.
- Never log unobfuscated values.
- Keep secret scope as short as possible.
